# Contributing

This is a focused React reference application for exploring clear, accessible, responsive page layouts and navigation. The conventions below apply to anyone touching the code.

## Principles

- **Accessibility first.** Use semantic structure, keyboard access, visible focus, and understandable names from the beginning.
- **Keep the app focused.** Add only components, pages, styles, configuration, or assets that support this React application.
- **Use the existing foundation.** Prefer the current layout components and shadcn primitives before creating a parallel implementation.
- **Mobile-first.** Pages reflow at 320px and remain readable and usable on smaller screens.
- **Plain, calm language.** Use clear names and practical page copy.
- **Small commits.** Keep one coherent concern per commit.

## Stack conventions

- TypeScript strict mode. No `any` without a comment explaining why.
- Tailwind v4 utility classes in JSX. Use the existing semantic CSS tokens rather than hard-coded colors.
- Use React Aria Components for interaction, focus management, and keyboard behavior.
- Preserve the history-based router and real anchor navigation in the reference app.

## Where code belongs

- Hand-written layout components go in `src/components/layout/`.
- shadcn-generated primitives go in `src/components/ui/`.
- Route-level pages go in `src/pages/`.
- Shared route and navigation data belongs in `src/pages/index.tsx`.
- Small shared utilities go in `src/lib/`.

See the relevant [directory README](./src/components/README.md) before adding or moving files.

## Component checklist

Before considering a component or page complete:

- [ ] TypeScript props are typed.
- [ ] Keyboard interaction works where relevant.
- [ ] Focus is visible and correctly managed.
- [ ] Semantic landmarks and accessible names are present.
- [ ] Light and dark themes remain usable.
- [ ] The page reflows at 320px without horizontal overflow.
- [ ] There are no console warnings.
- [ ] Exported components have useful JSDoc examples where the source pattern calls for them.

## Comments

For hand-written source:

1. Add a short file-level docblock describing the file's exports.
2. Use section headers for logical blocks.
3. Add inline comments only when they explain a non-obvious reason.
4. Add JSDoc to public exports when it improves editor guidance.

Do not add project-specific comments to files generated by shadcn; those files may be overwritten.

## Commit conventions

Use [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` — new page or component behavior
- `fix:` — bug fix
- `docs:` — README or source documentation
- `chore:` — tooling or configuration
- `refactor:` — behavior-preserving code change
- `test:` — test changes

Use present-tense imperative wording, for example:

```text
feat: add mobile navigation guide page
```

## Verification before committing

```bash
pnpm lint
pnpm build
git diff --check
```

Lint currently reports four accepted `react-refresh/only-export-components` warnings on legitimate co-located variant functions or hooks. Any additional warning or error needs investigation.

Also manually inspect the affected route at desktop and narrow widths. For navigation changes, check keyboard focus, mobile menu behavior, real links, active state, Escape, and focus return.

## Git operations

- Use `git mv` when renaming or moving files.
- Rebase or amend only local, unpushed commits.
- The repository currently works directly on `main`.
- Push only after local verification and review.
